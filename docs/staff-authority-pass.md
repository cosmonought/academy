# Academy staff authority pass

Status: implementation committed as `214b0df`; Functions and RTDB rules deployed and independently verified. See `staff-deployment-status.md` for deployment and live-test details.

## Implementation report

1. **Files changed:** `account.html`, `admin.html`, `profile.html`, `js/academy-auth.js`, `js/account-create.js`, `js/account-flow.js`, `js/account-page.js`, `firebase.json`, `firebase-rules-latest.json`, `tests/rules.mjs`, `tests/account-flow.test.mjs`. Added: `css/staff.css`, `js/staff-api.js`, `js/profile-teaching.js`, `js/admin-support.js`, `functions/package.json`, `functions/package-lock.json`, `functions/index.js`, `functions/staff-service.js`, `functions/shared/academy-record.js`, `functions/shared/seminar-data.js`, `functions/shared/seminar-policies.js`, `scripts/sync-staff-model.mjs`, `tests/staff-service.test.mjs`, `tests/staff-rules.mjs`, `tests/staff-ui.cjs`, and this report.
2. **Roles:** participant is the ordinary default; instructor is a seminar assignment; administrator retains the existing verified `academy@netadao.org` authority. These roles can overlap. No new account types or additional staff roles.
3. **Assignments:** `seminarStaff/{seminarId}/{authUid}` contains `role: "instructor"`, human-readable `email`, `assignedAt` (milliseconds), and `assignedBy` (admin UID). Only Admin-authorized callable functions can change this tree. Browser access to the tree is denied. `getTeachingAssignments` returns only the caller's seminar IDs; there is no duplicate registration database.
4. **Profile:** Attending remains the default and retains the participant record, attendance details, display name, evaluations, interests, attention notices, account controls, and footer. Teaching appears only for assigned accounts. One assignment opens directly; multiple assignments get a selector. The account section remains shared. Google-only users are not prompted to set an Academy password.
5. **Instructor enrollment:** assigned-seminar rosters show name, email, X handle, reason, policy information when recorded, and enrollment state. Enroll and Unenroll use the same shared path as Admin. Current Graphic policy acceptance is validated server-side before enrollment, matching the existing rule requirement. Enrollment confirmation reuses the existing best-effort EmailJS notification after a successful new enrollment; email failure does not undo enrollment. Instructors have no permanent deletion operation.
6. **Instructor attendance:** only enrolled participants in the assigned seminar can be changed. The backend validates exact canonical attendance-event keys and boolean marks. Lecture and screening events remain distinct. The UI shows Unrecorded, Attended, and Absent; the matrix scrolls within its region. The Graphic currently has no scheduled attendance events, so its attendance view states that rather than inventing events.
7. **Instructor evaluation:** where evaluation is offered, enrolled participants' requests can receive an agreed form, Agreed / In progress / Completed state, one of the established three outcomes, and up to 10,000 characters of written feedback. Instructors write only the `instructor` child and cannot rewrite the participant request. Completion requires an outcome. The backend requires an existing request for instructors; Admin retains exceptional correction authority.
8. **Admin enrollment:** global Enroll / Unenroll / re-enroll use the authenticated callable path. Unenrollment sets `enrolled: false`, preserving history and removing existing enrolled-only access. Admin attendance and evaluation controls also retain access to records after unenrollment for historical corrections.
9. **Permanent deletion:** Admin-only callable, preceded by a confirmation naming participant, email, seminar, and irreversible effects. It atomically deletes the seminar registration (including nested attendance) and matching evaluation. It preserves Auth identity, account metadata, other registrations/evaluations, and interests. The backend additionally requires a matching participant/seminar confirmation identifier. No Auth-user deletion exists.
10. **Assignment controls:** Account Assistance first resolves a real Firebase Auth account. Grant teaching access uses that UID; the server resolves the UID again and rejects missing/disabled accounts. Existing assignments can be revoked independently, leaving other assignments and enrollment intact.
11. **Account Assistance:** email lookup distinguishes Auth account existence from registration existence. Missing accounts and accounts without registrations have separate explanatory states. Name-based search and the optional email-instructions action were not added.
12. **Safe Auth metadata:** UID, email, verification, disabled state, provider IDs with human labels, creation date, last sign-in date, and a qualified password-status description. No hashes, passwords, tokens, reset URLs, or credential internals are returned. `password` is labeled Email, with legacy uncertainty explained.
13. **Recovery:** Email-provider accounts expose Send password setup/reset link using the existing Firebase reset email helper. Google-only accounts show Continue with Google instructions and no irrelevant reset action. Successful password creation and password sign-in now record `hasPassword`; missing legacy metadata remains Unknown / legacy account. A true flag is labeled as account metadata rather than an infallible Auth fact. Existing set-password tracking remains.
14. **Google sign-in:** Continue with Google is restored to the public account UI, with popup-cancelled/blocked feedback. New Google sign-ins enter the normal signed-in account/enrollment flow without automatic enrollment or a password requirement.
15. **Legacy Google identities:** the existing Firebase Google popup helper signs users into their Firebase identity. No alternate Academy identity creation or name/email-heuristic merge is introduced. Existing email-key registration ownership checks still require matching UID, or verified email for legacy unbound records.
16. **Provider conflicts:** `auth/account-exists-with-different-credential` explicitly directs the user to their existing email/password or password recovery. No manual provider-linking or merging code was added. `completeSignInIfNeeded()` is preserved and also called by the public account page for historical email-link compatibility.
17. **Backend:** a minimal Firebase Functions v2 callable layer with Admin SDK was required for secure roster filtering and Auth diagnostics. Ten explicit operations: `getTeachingAssignments`, `getTeachingRoster`, `staffSetEnrollment`, `staffSetAttendance`, `staffSetEvaluation`, `adminGetAuthSummary`, `adminListInstructors`, `adminAssignInstructor`, `adminRevokeInstructor`, `adminDeleteRegistration`. It is not an arbitrary database proxy.
18. **Deployment:** backend deployed and verified; see `staff-deployment-status.md`. The ordered instructions below document the required sequence. Existing Admin mutation helpers now depend on these functions, so the backend must be available before publishing the updated frontend.
19. **Rules:** deny-by-default retained; `seminarStaff` explicitly denies browser reads/writes; evaluation validation now accepts `in-progress`. The registration-root read rule, participant ownership protections, readings gates, general-signup access, and participant/staff field separation are unchanged. Instructor writes use the server, not broader RTDB grants.
20. **Targeted tests:** 20 Node tests passed across staff service, account flow, and attendance catalog; 14 database emulator tests passed across registration/evaluation rules and new instructor-denial tests. Function exports and changed JS/inline modules parse and load. `git diff --check` passed. One pre-existing Graphic registration test used whole-record `set` where field rules and the shared registration function use `update`; corrected that test's write pattern without loosening production rules. No full test suite was run.
21. **Responsive/accessibility:** Playwright with mocked Auth/callable responses checked Teaching at 1440, 1280, 1024, and 390 px: no page overflow, default Attending, assigned-only selector, evaluation save, and revoked-access fallback. Also checked ordinary participant without Teaching, mobile Admin account assistance/contained tables, Google conflict copy, and Google success into the account flow. Screenshots inspected at desktop/mobile. Semantic buttons/forms, labels, table headers, visible focus styles, `aria-pressed` mode state, status messages, and a keyboard-focusable attendance scroll region are provided. External web fonts were not loaded in the fixture. This is not a screen-reader audit or a live authentication test.
22. **Security verification:** unauthenticated requests, ordinary-participant staff requests, unassigned-seminar access, disabled callers, unverified Admin, invalid path keys/event keys/types, unauthorized deletion, and stale instructor assignments fail closed in targeted tests. Each privileged operation rechecks caller identity and current authorization. Roster responses contain only the requested seminar's allowlisted registration fields and evaluation; no general signups or account metadata. Safe Auth responses explicitly select fields. Admin SDK imports exist only under `functions/`; no credentials were introduced in browser code.
23. **Deliberately untouched:** homepage, seminar art/content/layout, Cinema art direction (chat identity/moderation was subsequently migrated as requested), general Admin art direction, general signups/proposals, existing reading gates and participant ownership rules. No LMS, submissions portal, messaging system, password-setting support tool, Auth deletion, or new role hierarchy. Live Google identity reuse, delivery of EmailJS/reset emails, and live deployed-function integration remain smoke tests for deployment. Older unrelated security/UX areas were not redesigned.

## Deployment order

Use an authorized Firebase deployment environment for project `neta-dao-cinema`. The source targets Node 22, callable region `us-central1`, with a maximum of five instances per function. Firebase Functions requires the appropriate project billing/IAM configuration. No service-account key belongs in the repository or frontend.

1. Verify the existing administrator Auth account has verified email. Enable/check Google as an Auth provider and the production site's authorized domain. Preserve the existing email/password and email-link recovery configuration.
2. Install the locked server dependencies: `npm ci --prefix functions`.
3. Regenerate the server's canonical event/evaluation model: `node scripts/sync-staff-model.mjs`. The deployment pre-hook also runs this; redeploy functions whenever the canonical attendance catalog changes.
4. Deploy the functions codebase and database rules: `firebase deploy --only functions:academy-staff,database --project neta-dao-cinema`.
5. Confirm that the ten callable functions are deployed successfully before publishing the updated static frontend. No new user roles are created automatically; Admin grants instructor assignments through Account Assistance.
6. Smoke-test with a real Admin, a single-seminar instructor, and an ordinary participant: scoped roster, cross-seminar denial, enroll/re-enroll notification, real attendance mark, evaluation, revocation, Google login (existing UID), and provider-appropriate reset delivery. Use test registrations for deletion; verify unrelated records remain.

If deployment fails, keep the old frontend running. Do not publish the new Admin mutation helpers before their backend exists.
